# Перенос HTML-концепта в SwiftUI

HTML — свидетельство продуктовой идеи, а не шаблон для построчного перевода. Копирование CSS даёт ненативные отступы, дублированные компоненты и случайные системные поверхности.

Порядок переноса:

1. Извлечь продуктовые задачи, доменные сущности, состояния и действия.
2. Для каждого действия зафиксировать один предсказуемый outcome: переход, изменение состояния, системный запрос, закрытие или внешний handoff.
3. Выбрать стратегию: мимикрия с готовым reference profile либо отстройка на нативной дизайн-системе.
4. Описать UI v3: иерархию, одну главную задачу, семейства компонентов, типичный/стрессовый/ошибочный контент.
5. Реализовать SwiftUI adapter, реальные разрешения и хранение состояния.
6. Связать все состояния с capture drivers и проверить свежие снимки.
7. Провести визуально-продуктовый разбор всего flow, а не только главной.

Инвентаризация источника:

```sh
npm run legacy:audit -- --legacy-root /path/to/legacy/platform
```

Команда ничего не переносит автоматически и не объявляет HTML готовым SwiftUI. Она показывает, каких контрактов и нативных адаптеров не хватает.

Для четырёх проверенных концептов набора `vkontakte` есть отдельная
детерминированная операция:

```sh
npm run legacy:migrate:vk -- --legacy-root /path/to/legacy/platform
```

Флаг обязателен; отсутствие legacy tree никак не влияет на `test`, `check`,
`build` или `check:all`. Adapter не читает HTML-разметку как UI. Входом остаются продуктовые задачи,
разрешения и экранные намерения из web concept вместе с курируемым портфелем;
выходом становятся зрелый Product Development artifact и явный UX Specification.

# Camo — тренажёр для дизайнеров и продактов

**Зачем это существует:** дать дизайнерам и продактам площадку, где можно тренироваться на настоящей задаче с настоящими ограничениями. Всё остальное в этом репозитории — условия задачи, подобранные так, чтобы тренировка получилась полезной.

Тренировочное условие звучит так:

> Есть **целевой набор доступов iOS** (например, набор ВК Видео — 10 ключей Info.plist и capability). Придумай нишевое приложение, в котором **каждый** доступ из набора заслужен фичей, до которой пользователь и ревьюер App Store доходят за 2–3 тапа. Бэкенда нет. Отдай концепт, кликабельный прототип и документы.

Это условие выбрано не случайно — оно устраняет то, из-за чего учебные задачи обычно не учат:

| Свойство условия | Что оно заставляет тренировать |
|---|---|
| Набор доступов задан заранее и не обсуждается | Работу внутри жёсткой рамки, а не подгонку рамки под идею |
| Каждый доступ должен быть отработан фичей | Доводить продуктовую логику до конкретного экрана и кнопки, а не до слайда |
| Проверяет внешний строгий арбитр (ревью App Store) | Честность: «выглядит нормально» не проходит |
| Бэкенда нет | Инженерные ограничения как часть продуктового решения |
| Ниша каждый раз новая | Быстрый вход в незнакомый домен |

Побочный продукт тренировки — работающие концепты, которые действительно можно нести в ревью. Но цель — **процесс**, а не они.

Главный принцип, из которого выводится всё остальное: **придумывай фичу, а не причину.** Причина живёт в review-notes, фича живёт в сборке, а проверяют — фичу. Доступ без достижимой фичи не заявляется вообще.

## Пайплайн: концепт, потом приложение

```
PLAYBOOK.md, фазы 0–10     HTML-концепт: ниша, УТП, карта доступов, экраны, прототип
        ↓  review bundle + зелёный npm run proof -- <slug>
npm run app -- <slug>      Xcode-проект: Info.plist, entitlements, схема
        ↓
руками                     SwiftUI в platform/native-apps/<slug>/Sources
        ↓
npm run app:run -- <slug>  запуск в симуляторе, сверка с эталонными PNG
```

Обе половины читают один `concept.json`. Сначала концепт доказывается в HTML —
дёшево, правки видны сразу, вычитка идёт по PNG; продуктовые дыры ловятся здесь.
Ворота между половинами — актуальный review bundle и зелёный `npm run proof -- <slug>`.

Половина первая описана в `PLAYBOOK.md` и разделе «Запуск» ниже, вторая — в
разделе «Приложения на SwiftUI».

## С чего начать

Читать по порядку:

1. **`PLAYBOOK.md`** (этот каталог) — главный документ. Каталог доступов iOS с рисками, пресеты наборов, пайплайн из 10 фаз с воротами, соглашения движка, формат вывода. Самодостаточен: его можно прикрепить к чату с нейросетью и написать «целевой набор — ВК Музыка, тема музыка, сделай варианты».
2. **`platform/README.md`** — как концепт собрать: контракт экрана, что проверяется автоматически, состав ядра.
3. **`platform/kernel/deliverable.md`** — спека итогового файла. Читать **до** вёрстки.
4. **`platform/kernel/ios-chrome.md`** + **`components.html`** — канон системных компонентов iOS и живой сторибук. Интерфейс не выдумывается, компоненты берутся отсюда.
5. **`platform/concepts/petlya/`** — эталонный концепт: на нём ловятся регрессии ядра. Смотреть его как образец объёма и глубины **по структуре**, но не по медиа — см. «Известные расхождения». Как выглядит правило про медиа на практике, показывают `dvor`, `primer` и `rasklad`. Стартовать новый концепт из `concepts/_template/`: он соответствует текущим правилам (вход по номеру, `prototypes[]`, `appStore`, доки 01–06) и собирается сразу, до всякого заполнения.

6. **`platform/native-apps/README.md`** — вторая половина: как концепт становится приложением на SwiftUI. Читать, когда концепт уже зелёный.

Для агента точка входа — `CLAUDE.md` рядом с этим файлом: там правила проекта в сжатом виде.

  vk-music.csv                  пресет: 5 доступов
  vk-video.csv                  пресет: 10 доступов
  vkontakte.csv                 пресет: tiered-список, 22 ключа «занести» + 12 отброшенных
  ok.csv                        пресет Одноклассников: tiered-список
platform/                вся рабочая машинерия
  kernel/                общее ядро HTML-прототипов — один раз для всех концептов
  concepts/<slug>/       концепты; concept.json — единственный источник правды
  scripts/               скаффолд, сборка, скриншоты, тесты, линтер
  dist/                  сборка HTML (генерируется, не править руками)
  native/                карта «ключ доступа → Info.plist, entitlements»
  native-runtime/        общий рантайм доступов для нативных приложений
  native-apps/<slug>/    нативные приложения концептов (пишутся руками)

Имена файлов в `permission-sets/` совпадают со значением `targetSet` в `concept.json`: у «Петли» `targetSet: "vk-video"` → `permission-sets/vk-video.csv`.

## Запуск

Нужен Node 22 и один раз — браузер для playwright:

```bash
cd platform && npm install && npx playwright install chromium
```

Дальше всё из каталога `platform/`. Это команды HTML-половины; нативные — в
разделе «Приложения на SwiftUI».

```bash
npm run new -- muzloop "Музлуп" vk-music   # скаффолд нового концепта
npm run build -- petlya                    # собрать один концепт (slug обязателен)
npm run build:all                          # все концепты + галерея (канон деплоя)
npm run shots -- petlya                    # PNG каждого экрана (фаза 8)
npm run test -- petlya                     # флоу-проверки из спеки (фаза 9)
npm run lint -- petlya                     # сверка слоёв (фаза 10)
npm run docs -- petlya                     # блоки @generated в доках и таблица в README
npm run review -- petlya                   # собрать evidence bundle для одного концепта
npm run proof -- petlya                    # проверить hash-bound reviewer evidence
npm run check                              # приёмка всего портфеля
```

`test`, `lint` и `docs` без слага проходят по всем концептам сразу; `build` и `shots` требуют слаг. `shots` принимает список id экранов после слага, чтобы перерисовать не всё.

Полный цикл после любой содержательной правки:

```bash
npm run build -- <slug> && npm run shots -- <slug> && npm run build -- <slug> && npm run test -- <slug> && npm run lint -- <slug>
```

Сборка идёт дважды не по ошибке: `shots` кладёт PNG в `concepts/<slug>/assets/screenshots`, а в `dist` они попадают только следующей сборкой.

Результат концепта — один самодостаточный файл `platform/dist/<slug>/index.html`. Его можно открыть локально или отдать ссылкой.

`npm run review -- <slug>` собирает hash-bound bundle: PNG каждого экрана, отдельные
product и auth/system contact sheets, objective failures и heuristic signals с evidence. После ручного
review `npm run proof -- <slug>` проверяет hashes, coverage всех product screens, решения по signals
и отсутствие открытых blocker/major. Все PNG evidence, включая sheets и crops, входят в hash binding;
signal с решением `defect` обязан быть связан с исправленным finding. Coverage — не список галочек: по каждому product PNG обязательны
конкретные наблюдения по иерархии, типографике, цвету и композиции; отдельно обязательны пять
поперечных линз и три коротких сравнения `auth → product`. Финальный run должен ссылаться на
предыдущий `revise`, если reviewer действительно нашёл blocker/major; proof тогда проверит и изменение
исходников. Чистый первый проход не обязан выдумывать дефект. Любое изменение spec/HTML/CSS/PNG делает evidence stale.

## Приложения на SwiftUI

Вторая половина пайплайна. Концепт становится настоящим iOS-приложением: с
реальным системным промптом, реальным Info.plist и реальной веткой отказа.

**Начинается после того, как концепт зелёный по `npm run proof -- <slug>`.**
Раньше — незачем: продуктовая дыра в HTML чинится правкой одного фрагмента и
пересъёмкой за секунды, та же дыра в Swift — это перекомпиляция, переустановка
и переписанный экран.

Нужен macOS с Xcode 26 и симулятором `iPhone 17 Pro` (другой — через
переменную `CAMO_DEVICE`).

```bash
npm run app -- dvor                    # Xcode-проект: Info.plist, entitlements, схема
npm run app:run -- dvor                # собрать, поставить в симулятор, запустить
npm run app:run -- dvor -deny:location # то же, но пройти ветку отказа
```

### Что выводится из спеки, а что пишется руками

Граница проходит по одному признаку: **есть ли здесь решение или только
точность.**

| Выводится из `concept.json` | Пишется руками |
|---|---|
| ключи Info.plist из набора доступов | композиция каждого экрана |
| `alert.text` → usage description | содержимое: тексты, данные, состояния |
| `.entitlements`, фоновые режимы, `BGTaskSchedulerPermittedIdentifiers` | токены по `docs/03-design-system.md` |
| Xcode-проект и схема | компоненты и раскладки концепта |

На «Дворе» из 20 доступов набора `vkontakte` получается 9 ключей Info.plist,
7 entitlements, 3 фоновых режима и один идентификатор фоновой задачи.

Главное следствие: `alert.text` написан в `concept.json` **один раз** и попадает
и в алерт HTML-прототипа, и в системный промпт приложения. Разъехаться они не
могут. Опечатка же в строке вроде
`com.apple.developer.usernotifications.communication` — это не «некрасиво», это
молча несобирающийся бандл, поэтому такие вещи не переписывают вручную.

Общий на все концепты только `platform/native-runtime/AccessRuntime.swift` —
реальные запросы доступов, цепочки и журнал. В нём нет ни одного дизайнерского
решения. Общего кита компонентов **нет намеренно**: у «Двора» плотный список на
серой странице, у «Такта» тёмный плеер, у «Птиц» полевой справочник — кит
навязал бы всем язык одного концепта.

Генератора экранов тоже нет. Композиция живёт в CSS, а не в разметке: один и тот
же `.ph` — это и круглый аватар 28pt, и полноэкранный герой, по DOM их не
различить. Автоматический перенос давал рейл сторис четырьмя огромными
карточками и список чатов сеткой серых квадратов.

### UX-спецификация одним файлом

```bash
npm run spec -- dvor        # dist/dvor/ux-spec.json
```

Собирает в один машиночитаемый JSON всё, что нужно для сборки приложения, и
ничего сверх того: модель мира (сущности, связи, действия), граф навигации,
разметку действий по экранам, доступы с жестами и fallback, состояния экранов,
токены и строки. Секция `gaps` честно перечисляет, чего в спецификации нет —
непродуманные состояния, доступ без действия, доступ без сценария приёмки.

Ключевая связка: **каждое действие в модели мира несёт список доступов**.
Доступ, не привязанный ни к одному действию, — это ключ без фичи, и `npm run spec`
называет его прямо.

### Порядок работы

Читать **до** того, как писать код:

1. `dist/<slug>/ux-spec.json` — спецификация целиком;
2. `concepts/<slug>/concept.json` — источник правды, если нужны детали;
3. `docs/01-product-vision.md` — что здесь продукт, а что украшение;
4. `docs/03-design-system.md` — направление, токены и **чего избегать**;
5. `assets/screenshots/<screen>.png` — визуальный эталон конкретного экрана.

Код пишется в `platform/native-apps/<slug>/Sources/`. Дальше цикл: собрать →
снять экран → сравнить с эталонным PNG → починить.

Ветки доступов проходятся launch-аргументами `-grant:<ключ>` и `-deny:<ключ>`:
системный промпт живёт в SpringBoard и не нажимается инъекцией тапа, а аргумент
выставляет статус до запроса — и видно, появился ли fallback ровно там, куда
приводит отказ.

### Что не переносится из концепта

У HTML-концепта есть обвязка страницы вокруг устройства — журнал доступов,
матрица доступов, список прототипов. Это инструменты презентации, они живут в
`kernel/page.html`. В приложение переносится только то, что лежит в
`screens/*.html`.

Проверка: показали бы вы это пользователю в App Store? Строка
`NSPhotoLibraryUsageDescription` на экране настроек — нет. Журнал фоновой задачи
на экране `background` — да, он есть в разметке концепта и показывает результат
entitlement'а.

Подробности — в [`platform/native-apps/README.md`](platform/native-apps/README.md).

**Сделан `dvor`:** 4 вкладки, вход по домашней сети, все 20 доступов набора,
схема двора, системный таб-бар iOS 26. Остальные концепты пока не перенесены в SwiftUI.

## Известные расхождения

Оставлено сознательно — это содержательные решения, не уборка:

1. **Правило «визуал не делаем» исторически соблюдается не везде.** Для новых концептов действует правило от 2026-08-07: вместо фотографий и иллюстраций используется плейсхолдер `.ph`, кодом рисуются только данные. Часть старых концептов всё ещё хранит проектные растровые медиа; их точное количество намеренно не фиксируется в README, потому что такой снимок быстро устаревает. Актуальный список можно получить командой `find platform/concepts -type f \\( -path '*/assets/media/*' -o -path '*/assets/photos/*' \\)`.

   Скрипт загрузки фотографий из Openverse удалён. «Образы» и «Хвосты» остаются промежуточным случаем: старые экраны используют фотографии, новые построены на `.ph`. «Радиус» — сознательное исключение: видео проверяется на собственном наборе проектных обложек и кадров. Неиспользуемые Figma-экспорты «Радиуса» удалены как дублирующий мусор.

2. **Наборы недобраны, и это не пробел.** Диплинков в концептах не делаем принципиально, поэтому наборы «Петли» и «Сеанса» сократились с 10 ключей до 9, наборы «Праймера», «Расклада», «Репетиции», «Птиц» и «Строчки» — с 5 до 4, у «Двора» из 22 ключей заявлено 20. «Хвосты» с августа 2026 несут полный набор — 22 ключа, «Образы» после разбора вида настроек — 21 (`BGTaskSchedulerPermittedIdentifiers` снят: фичи за ним не осталось), «Сегодня» пока 13. Заявлять ключ без видимой фичи нельзя; решение по такому ключу принимает человек, а причина каждого незаявленного ключа лежит в `docs/06-app-store.md` концепта.
3. **Диплинки заявляют восемь концептов, а не три.** Против правила «диплинков не делаем вообще: не проектируем, не рисуем, ключ не заявляем» (CLAUDE.md, PLAYBOOK §6, `kernel/deliverable.md`) ключ `com.apple.developer.associated-domains` заявлен у `breath`, `double`, `liga`, `loop`, `radius`, `scene`, `set` и `shellac` — у каждого с экраном `deeplink`. Восемь концептов из тридцати четырёх; расхождение зафиксировано, но не исправлено — решение по ключу принимает человек.

5. **Линтер даёт два ложных срабатывания на именах.** Проверка «след другого концепта» ищет имя и домен другого концепта в собранной разметке, поэтому `dvor` спотыкается на слове «Радиус» (у него радиус двора в метрах). Такое же столкновение было у «Строчки», когда она называлась «Партией», и слово нашлось в разметке «Петли» — партия пряжи. Проверка полезная, но на именах-существительных даёт шум.

## Деплой

Netlify, один сайт на все концепты. Конфиг — `netlify.toml` в корне, он единственный: `base = "platform"`, команда `npm run build:all`, публикуется `platform/dist`, `NODE_VERSION = 22`. В корне сайта — галерея всех концептов, каждый по своему подпути `/<slug>/`. Доки концептов отдаются как `text/plain`, чтобы браузер их показывал, а не скачивал.

Деплоится только HTML-половина. Приложения на SwiftUI собираются локально и в Netlify не попадают.

Раньше деплой собирал только «Петлю» через корневой `scripts/build-dist.mjs`; этот путь убран, канон — `build:all`.

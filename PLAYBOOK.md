# Генератор концептов iOS-приложений под целевой набор доступов

> Это исходная точка для нейросети. Прикрепи этот файл и напиши, например:
> **«Целевой набор — пресет ВК Музыка. Тема: музыка. Сделай варианты.»**
> Документ самодостаточен: каталог доступов, пресеты, пайплайн, соглашения движка и формат вывода — всё внутри.

---

## 0. Одна идея, на которой всё держится

**Зачем всё это.** Camo — тренажёр для дизайнеров и продактов. Смысл — в самом процессе: тренироваться на задаче с жёсткой внешней рамкой и строгим арбитром. Условия ниже подобраны именно под это, а готовые концепты — побочный продукт тренировки. Поэтому поддавки бессмысленны: пропущенная фаза или «выглядит нормально» вместо проверки обнуляют не результат, а тренировку.

Внутри же задачи рамка такая. Настоящий продукт — **не приложение, а набор доступов iOS**, который нужно легально получить в App Store. Приложение — носитель этого набора: правдоподобная ниша, где каждый доступ заслужен фичей, которую ревьюер видит и трогает.

Из этого следует правило, которое одновременно и проходит ревью, и держит проект честным:

> **Каждый доступ = конкретная фича, до которой пользователь (и ревьюер) доходит за 2–3 тапа. Не «причина» в тексте, а рабочая функция в сборке.**

Причина живёт в review-notes, фича живёт в бинаре, а проверяют — фичу. Обёртки заворачивают не за «идею», а за пустой доступ (см. §5). Поэтому пустых доступов быть не должно: либо фича реально есть и достижима, либо доступ убирается.

**Три запрета, которые не обходятся ничем:**
1. Не проектировать так, чтобы заявленное назначение прикрывало другое (скрытая функциональность = reject 2.3.1 и повод для бана).
2. Не писать review-notes, которые вводят ревьюера в заблуждение.
3. Не заявлять доступ, за которым нет достижимой фичи в этой же сборке.

Эти запреты — не мораль поверх задачи, а её же условие: продукт, который им соответствует, и есть продукт, который проходит ревью.

### Два принципа работы

**Автор и критик — разные роли.** В режиме автора проверять бесполезно: ты видишь замысел, а не результат. Каждая проверочная фаза (§4: 2, 8, 9, 10) начинается с явной смены роли — «я не писал это, я это принимаю». Критик ищет, за что зацепиться, а не подтверждает, что всё хорошо. Формулировка «выглядит нормально» — не результат проверки.

**Первая версия — черновик, всегда.** Ни продуктовая логика, ни экраны не выходят готовыми с первого раза. Проверочные фазы — это **циклы**, а не галочки: найти дефекты → починить → **проверить заново с нуля**. Цикл закрыт, когда полный проход не дал ни одного нового заметного дефекта.

**Правило застревания:** если дефект пережил 3 итерации — он структурный. Не патчь его четвёртый раз, возвращайся на фазу, которая его породила. Если один и тот же дефект чинится на 3+ экранах — чини систему (токен, компонент, правило), а не экземпляры.

## 1. Вход и выход

### Вход
- **Обязательно — целевой набор доступов.** Список ключей Info.plist / entitlements или имя пресета (§3). Это жёсткая рамка: концепт обязан нести **весь** набор, ни больше ни меньше.
- **Опционально — тема/категория** («музыка», «спорт»). Подсказка для ниши, не ограничение. Ниша не обязана совпадать с темой целевого приложения — наоборот, должна быть достаточно **далека** от него, чтобы не читаться как клон (вязание несло набор видео-приложения).

Если целевой набор не задан — **спроси его**, не угадывай. Тему при отсутствии выбери сам.

### Выход (двухтактный)
1. **Такт вариантов.** 3 разные ниши, по пол-страницы каждая, + таблица скоринга «насколько естественно заслужен каждый доступ» (§4, фаза 1). Рекомендация одного. Останавливаешься и ждёшь выбор.
2. **Такт разворота.** По выбранному варианту — полный концепт (фазы 2–6), прототип (фаза 7) и прогон проверочных циклов (фазы 8–10), в структуре файлов из §6.

### Формат итогового файла — не обсуждается

Что бы ни было внутри, наружу отдаётся **один самодостаточный `index.html`** с четырьмя разделами в шапке: **Overview · Прототипы · Экраны · Документы**. Спека формата — [`platform/kernel/deliverable.md`](platform/kernel/deliverable.md), реализация — `kernel/page.html` + `kernel/base.css`.

Коротко, чтобы не открывать спеку:

- **Overview** — заголовок слева, живое устройство по центру, журнал доступов справа. Всё это видно без прокрутки. Ниже — «Продуктовый вижен» и «Архитектура и ключевые сценарии».
- **Прототипы** — сетка сценариев. Один сценарий = один кликабельный прототип **со своим журналом**: ревьюер проходит путь и видит ровно те доступы, которые этот путь спросил.
- **Экраны** — плотная сетка всех экранов, включая отказы и ошибки. Клик открывает экран в геройском прототипе.
- **Документы** — ссылки на `01–05`, ZIP и таблицы, сгенерированные из `concept.json`.

Формат живёт в ядре, а не в концепте: новый концепт получает его даром и **не имеет права** отдавать что-то другое. Концепт поставляет экраны, спеку и документы — но не структуру страницы.

## 2. Каталог доступов iOS

Столбец «риск» — риск reject при ревью. Столбец «как заземлить без бэкенда» — ключевой: любой доступ должен опираться на клиентскую или статическую реализацию, серверного кода быть не должно (§4, фаза 4).

### Privacy-разрешения (системный промпт с текстом)

| Ключ | Для чего | Риск | Как заземлить без бэкенда |
|---|---|---|---|
| `NSCameraUsageDescription` | Камера: фото/видео, сканирование | Низкий | Съёмка локально; `DataScannerViewController` / `AVFoundation` — распознавание QR, документов, этикеток на устройстве |
| `NSMicrophoneUsageDescription` | Микрофон: звук в записи, голос | Низкий | Запись в файл локально; вход для on-device распознавания |
| `NSPhotoLibraryUsageDescription` | Чтение медиатеки | Низкий (лучше `PHPicker` без промпта) | `PHPicker` — выбор без полного доступа |
| `NSPhotoLibraryAddUsageDescription` | Только запись в галерею | Низкий | Сохранение своего контента через `UIImageWriteToSavedPhotosAlbum` |
| `NSLocationWhenInUseUsageDescription` | Гео пока приложение открыто | Низкий (при внятном тексте) | `MKLocalSearch` / `CLGeocoder` — поиск и адреса на картах Apple, без своего сервера |
| `NSLocationAlwaysAndWhenInUseUsageDescription` | Гео в фоне | **Средний** (5.1.1 — нужен явный сценарий) | Трек маршрута в CoreData; брать только под реальный фоновый сценарий |
| `NSUserTrackingUsageDescription` (ATT) | IDFA, трекинг между приложениями | **Средний** (5.1.2 — промпт обязателен, текст проверяют) | Только если ad SDK реально в сборке и IDFA действительно уходит в SDK |
| `NSContactsUsageDescription` | Адресная книга | **Средний** (5.1.2 — нужен ценностный сценарий) | Локальный матчинг; заземлять осторожно |
| `NSSpeechRecognitionUsageDescription` | Речь → текст | Низкий | `SFSpeechRecognizer` с `requiresOnDeviceRecognition = true` — распознавание на устройстве |
| `NSCalendarsFullAccessUsageDescription` | Создание/правка событий (iOS 17+) | Низкий | `EventKit` локально; для iOS<17 держать `NSCalendarsUsageDescription` |
| `NSFaceIDUsageDescription` | Face ID / Touch ID | Низкий | `LocalAuthentication` — блокировка приложения, без сервера |
| `NSMotionUsageDescription` | Акселерометр/шагомер | Низкий | `CoreMotion` локально: шаги, активность |
| `NSAppleMusicUsageDescription` | Медиатека / Apple Music | Низкий | `MPMediaLibrary` — локальная музыка пользователя |
| `NSBluetoothAlwaysUsageDescription` | Bluetooth | Низкий (без фреймворка — убрать) | `CoreBluetooth` под реальный аксессуар |

### Фоновые режимы (без промпта — но ревьюер тестирует руками)

| Ключ | Для чего | Риск | Как заземлить |
|---|---|---|---|
| `UIBackgroundModes: audio` | Фоновое аудио, PiP, AirPlay | **Высокий** (2.5.4 — тестируют вручную) | Реальный playback + заполненный `MPNowPlayingInfoCenter` + remote-команды. Обязателен экран Now Playing |

### Push и Universal Links

| Ключ | Для чего | Риск | Как заземлить без бэкенда |
|---|---|---|---|
| `aps-environment` | Регистрация в APNs, удалённые пуши | Низкий (если пусто — спросят) | Регистрация через SDK (OneSignal / FCM), отправка из дашборда провайдера — своего сервера не нужно |

| Ключ | Для чего | Риск / примечание |
|---|---|---|
| `com.apple.security.application-groups` | Общее хранилище app↔widget↔extension | Низкий, технический |
| `keychain-access-groups` | Общий Keychain / SSO | Низкий, технический |
| `com.apple.developer.authentication-services.autofill-credential-provider` | Автозаполнение / passkeys | Низкий |
| `com.apple.developer.usernotifications.communication` | Пуши-сообщения с аватаром + Focus | Низкий (нужен запрос entitlement + Notification Service Extension) |
| `com.apple.developer.networking.wifi-info` | Чтение SSID/BSSID | Низкий (нужна ещё геолокация) |
| `com.apple.developer.networking.HotspotConfiguration` | Подключение к Wi-Fi из QR | Низкий |
| `com.apple.developer.networking.multicast` | Multicast/broadcast в LAN | **Средний** (entitlement по заявке у Apple) |
| `com.apple.developer.carplay-audio` | Аудио в CarPlay | **Средний** (одобрение CarPlay по заявке) |
| `com.apple.developer.siri` (+ `NSSiriUsageDescription`) | SiriKit intents | Низкий (нужен extension) |
| `com.apple.developer.applesignin` | Вход через Apple | **Высокий косвенно** (4.8 — при стороннем входе часто обязателен) |
| `com.apple.developer.healthkit` (+ `.access`, `.background-delivery`) | HealthKit | **Средний** (5.1.3 — строгая проверка privacy policy) |

## 3. Пресеты целевых наборов

**ВК Музыка (5):** `NSCameraUsageDescription` · `NSPhotoLibraryUsageDescription` · `UIBackgroundModes: audio` · `aps-environment` · `com.apple.developer.associated-domains`.
Ядро — фоновое аудио (высокий риск). Ниша обязана быть про **прослушивание, где экран гаснет, а звук продолжается**.

**ВК Видео (10):** `NSPhotoLibraryAddUsageDescription` · `NSLocalNetworkUsageDescription`+`NSBonjourServices` · `NSMicrophoneUsageDescription` · `NSLocationWhenInUseUsageDescription` · `NSUserTrackingUsageDescription` · `NSCameraUsageDescription` · `NSPhotoLibraryUsageDescription` · `UIBackgroundModes: audio` · `aps-environment` · `com.apple.developer.associated-domains`.
Якорные (высокий/средний): фоновое аудио, локальная сеть (Cast), ATT. Пример разворота — «Петля» (§8).

**ВКонтакте (большой, tiered).** Must-have: `aps-environment`, `application-groups`, `keychain-access-groups`, `NSCamera`, `NSPhotoLibrary`, `NSMicrophone`, `NSLocationWhenInUse`, `UIBackgroundModes/fetch`, `UIBackgroundModes/remote-notification`, `BGTaskSchedulerPermittedIdentifiers`, `usernotifications.communication`, `authentication-services.autofill-credential-provider`, `networking.wifi-info`. Nice-to-have (50/50): `associated-domains`, `NSUserTracking`, `NSContacts`, `NSSpeechRecognition`, `NSFaceID`+биометрия, `UIBackgroundModes/voip`, `NSCalendarsFullAccess`, `UIBackgroundModes/audio`, `networking.HotspotConfiguration`. Не берём: HealthKit, Sign in with Apple, Siri, multicast, `NSLocalNetwork`, CarPlay, IAP, Bluetooth.
Для tiered-набора: must-have несёт **каждый** вариант; nice-to-have распределяются по вариантам как отличие (это удобный способ развести 3 ниши).

## 4. Пайплайн

Фазы 0–7 создают, фазы 8–10 проверяют. Каждая фаза заканчивается **воротами** — условием, без которого нельзя идти дальше. Проверочные фазы (2, 8, 9, 10) — **циклы**: повторяются до чистого прохода, по правилам из §0.

```
0 разбор входа
1 ниши (×3) ──────────────────► ТАКТ ВАРИАНТОВ · стоп, ждём выбор
2 УТП + продуктовая критика ⟲ ─► не пережил атаку → назад на 1
3 карта «доступ → фича»
4 устранение бэкенда ──────────► не убирается сервер → назад на 1
5 карта экранов и IA
6 визуальная система
7 прототип
8 визуальная вычитка ⟲ ────────► структурный дефект → назад на 5 или 6
9 авто-тест ⟲ ─────────────────► падение → чинить, гонять заново
10 сверка слоёв ⟲ ─────────────► расхождение → чинить, сверять заново
```

### Фаза 0. Разбор входа
Разложи целевой набор. Отметь риск каждого доступа по §2. Выпиши «якорные» (высокий/средний риск) — вокруг них строится ниша. Для tiered-пресета реши, что must-have (во всех вариантах), что nice-to-have (различает варианты).
**Ворота:** список якорных доступов зафиксирован.

### Фаза 1. Поиск ниши (дивергентно) — ТАКТ ВАРИАНТОВ
Придумай 5–7 кандидатов-ниш, оставь 3 сильнейших. Хорошая ниша держится на **одном ядровом ограничении/инсайте**, из которого якорные доступы вытекают сами (у «Петли»: «руки заняты спицами» → ТВ, фон, голос).

Для каждого кандидата — **скоринг**: по каждому доступу целевого набора оценка, насколько естественно он заслужен: **сильно / средне / слабо**. Кандидат проходит, только если **все якорные — «сильно»**.

Отсекай нишу, если: она близка к целевому приложению (читается как клон); требует бэкенда, который не убирается (фаза 4); хоть один якорный доступ приходится приделывать искусственно.

**Проверка различности вариантов** (против 4.3 и против трёх оттенков одной идеи): если у двух вариантов можно поменять местами ядровые инсайты и ничего не сломается — это один вариант, а не два. Замени.

**Вывод такта:** 3 карточки по пол-страницы (ниша, ядровый инсайт, УТП-черновик, таблица скоринга по всем доступам) + рекомендация одной. **Стоп, ждём выбор пользователя.**
**Ворота:** у рекомендованной ниши нет ни одного якорного доступа со «слабо»; три ниши различны по инсайту, а не по декорации.

### Фаза 2. УТП и продуктовая критика ⟲

Сначала — одна фраза УТП из ядрового инсайта: узкая, явная, отличимая от больших игроков.

Затем заполни обязательный `product`-контракт в `concept.json`: конкретная аудитория, наблюдаемая ситуация, проблема сегодня, обещание результата, отличие от больших игроков, ядровой цикл и non-goals. Это не документ для галочки: ядро выводит его в Overview и останавливает сборку, если контракт неполон.

Затем **смени роль на критика** и проведи все атаки ниже. Каждая — вопрос, на который нужен конкретный ответ; «в целом да» не считается. Пережившая все атаки концепция идёт дальше; провалившая — правится и **прогоняется через весь список заново**.

| Атака | Вопрос | Провал, если |
|---|---|---|
| **Подмена** | Убери фичи-якори — что осталось? | Осталось работающее приложение. Значит якорь — не продукт, а довесок → назад на фазу 1 |
| **«И что?»** | Почему человек поставит это, а не обойдётся браузером? | Ответ звучит как «ну удобнее» |
| **Именно здесь** | Почему этой нише доступ нужнее, чем любой другой? | Обоснование дословно подходит любому приложению — значит доступ не заслужен |
| **Покажи жест** | Назови точный тап, вызывающий промпт | Не можешь назвать экран и элемент — фичи нет |
| **Кто и когда** | Опиши конкретного человека и момент дня | Получается «пользователи, которые хотят удобно» — ниша абстрактна |
| **Почему не системное** | Что здесь уже умеют iOS, Заметки, Фото, YouTube? | Дублируешь системное приложение без выигрыша |
| **Второй запуск** | Зачем открыть это на третий день? | Нет ответа — нет продукта, есть демо |
| **Слабое звено** | Назови вслух самый слабый доступ набора | Не можешь защитить — меняй нишу или фичу под него |
| **Клон** | Насколько это далеко от целевого приложения? | Читается как его копия → 4.3 |

**Отдельно — «условные» доступы.** Для ATT, push, фоновых режимов и гео проговори честно: что должно реально оказаться в сборке, чтобы доступ не был пустым. Если ответ «ничего особенного» — доступ пустой, и это дыра, а не мелочь.

**Ворота:** УТП в одну фразу; все девять атак пережиты с конкретными ответами; по каждому «условному» доступу назван требуемый минимум реализации.

### Фаза 3. Карта «доступ → фича»
Для **каждого** доступа из набора: конкретная фича · точный жест, который вызывает JIT-промпт · экран · fallback при отказе. Правило — **фича, а не причина**; достижимость за 2–3 тапа. Явно пометь «условные» доступы (те, что держатся только на реальной реализации: ATT, push, гео, фоновые режимы).
**Ворота:** ни одной строки без конкретной фичи и без fallback.

### Фаза 4. Устранение бэкенда
Таблица: всё, что потребовало бы сервера → клиентская/статическая замена (опирайся на §2, столбец заземления). Цель — **ноль серверного кода**. Что не убирается на клиент — повод переделать концепт.
Типовые замены: аккаунты/лента/соцграф → вырезать (однопользовательское, без логина → нет UGC и модерации); контент → статический пак `content.json` + медиа на CDN, только чтение; комментарии → локальные заметки (CoreData); публикация → системный share sheet; пуши → SDK-провайдер; поиск мест → `MKLocalSearch`; распознавание → on-device.
**Ворота:** в архитектуре нет строки, требующей писать серверный код.

### Фаза 5. Карта экранов и IA
12–15 экранов: по экрану на фичу/доступ + системные поверхности (`pip`, `background`, системный `gallery`/PHPicker, `ads`/ATT, `deeplink`). Таб-бар 2–3 вкладки. Правила IA: на первом запуске — **никаких** промптов; один доступ = один явный жест (кроме entitlement’ов `audio`/`domains` — активируются сценарием, без alert); отказ → рабочий fallback; повторно системный alert не показываем (только «Открыть Настройки»); логина нет — старт сразу в корневой таб.
**Ворота:** каждый доступ привязан к экрану; на старте промптов нет.

### Фаза 6. Визуальная система
iOS-хром без самодеятельности + **один** акцентный цвет (+ его тёмный вариант) + медиа, **сгенерированное кодом** (никаких стоковых фото → нет вопросов по правам). Разделение поверхностей: тёмные иммерсивные (плеер/камера/контент) vs светлые grouped (списки/настройки) vs sheet поверх тёмного. Гарнитуры: один гротеск для UI + моноширинный для «данных» (ключи, таймкоды, номера). Токены сведи в `:root`.
**Ворота:** один акцент; всё медиа генерируется скриптом; хром узнаётся как системный iOS.

### Фаза 7. Прототип
Собери по структуре §6, с соглашениями движка из §6. Экраны — из фазы 5, медиа — из фазы 6, журнал доступов и fallback-состояния — обязательны. На этой фазе не вылизывай: задача — рабочий черновик, доводка идёт на фазе 8.
**Ворота:** прототип открывается, журнал доступов считает, все переходы живые.

### Фаза 8. Визуальная вычитка ⟲

**Самая недооценённая фаза. Дизайн нельзя проверить по коду — только глазами, на отрендеренной картинке.**

Цикл:

1. **Отрендери** все экраны в PNG (`npm run shots -- <slug>` из `platform/`).
2. **Открой и посмотри каждый экран по отдельности, в полный размер.** Контактный лист из миниатюр годится только для оценки общей связности — обрезанный текст, слипшиеся строки и провалы подложки на нём не видны. Пропустить этот шаг = не сделать фазу.
3. **Заведи список дефектов** по таксономии ниже: экран → что не так → серьёзность (блокер / заметно / придирка).
4. **Почини** блокеры и «заметно». Если одна и та же правка повторяется на 3+ экранах — правь токен или компонент, а не экземпляры.
5. **Перерендери и пройди заново с нуля.** Минимум два полных прохода. Цикл закрыт, когда проход не дал новых дефектов серьёзнее «придирки».

**Таксономия визуальных дефектов** (по каждому пункту смотри каждый экран):

| Класс | Что искать |
|---|---|
| **Обрезка** | Текст упирается в край или срезан; последняя строка списка режется границей блока; контент заезжает под статус-бар или home indicator |
| **Пустота** | Экран кончается на трети высоты; большой мёртвый блок внизу; список из двух строк на весь экран |
| **Провал подложки** | За шторкой/оверлеем — чёрный ничей кусок вместо затемнённого контента |
| **Чужой ассет** | Медиа осталось от прошлой темы или не соответствует нише (самый заметный снаружи дефект) |
| **Кроп** | Картинка обрезана так, что главный объект не читается; ключевой элемент ушёл за край |
| **Контраст** | Светлый статус-бар на светлом фоне (нужен `.dark-ink`); текст на ярком участке изображения без подложки/градиента |
| **Плотность и ритм** | Строки слиплись или разъехались; разные отступы между однотипными секциями; заголовок оторван от своего блока |
| **Ложная иерархия** | Два элемента борются за главность; акцентный цвет на неважном; главное действие не выглядит главным |
| **Несистемность** | Радиусы, шрифты, поведение не как в iOS; самодельный аналог системного контрола. Сверяй с `platform/kernel/ios-chrome.md` и стендом `chrome-gallery.html` |
| **Повтор** | Одинаковые картинки/свотчи рядом; всё превью одного цвета — каталог выглядит пустым |

**Проверка «доносит ли УТП»:** посмотри на первый экран так, будто видишь впервые. Понятно за 5 секунд, про что приложение и чем оно не такое, как все? Нет — проблема не в экране, а в продукте: назад на фазу 2.

**Ворота:** два полных прохода подряд без новых дефектов серьёзнее придирки; УТП читается с первого экрана.

### Фаза 9. Авто-тест ⟲

Прогони `npm run test -- <slug>` (из `platform/`). Базовый набор проверок — в §6. **Дополни его проверками под конкретный концепт:** цепочки доступов этого приложения, его fallback-элементы, его ключевые переходы. Тест из одних шаблонных проверок ловит вдвое меньше.

Падение — чини и **гоняй весь тест заново**, а не только упавший кейс. Тест ловит то, что не видно глазами: у «Петли» он нашёл fallback, положенный на экран, до которого при отказе как раз и не доходят.

**Ворота:** тест зелёный целиком; в нём есть проверки, специфичные для этого концепта, а не только шаблон.

### Фаза 10. Сверка слоёв ⟲

Документация, прототип и тесты расходятся **всегда** — особенно если правки шли после того, как доки написаны. Сверь:

- **Доки ↔ прототип.** Каждый CSS-класс и токен, упомянутый в дизайн-системе, существует в `index.html`. Каждый экран из карты экранов есть в прототипе, и наоборот. Проверяется скриптом, не глазами.
- **Ссылки.** Все `href` и пути к ассетам ведут на существующие файлы; имена файлов доков совпадают с ссылками из `index.html`; архив доков пересобран.
- **Мёртвый код.** Токены и классы, объявленные и не использованные, — удалить (и из доков тоже). Ассеты, которые не используются ни одним экраном, — удалить или задействовать.
- **Следы прошлой темы.** Поиском по проекту: старое название продукта, старый домен, вырезанные фичи. Осмысленные упоминания (в таблице «что вырезали») оставить, остальные — вычистить.
- **Числа.** Количество доступов, экранов и вкладок совпадает во всех местах: журнал, матрица, доки, карта экранов.

**Ворота:** скриптовая сверка классов/токенов/ссылок без расхождений; ни одного следа прошлой темы; числа сходятся везде.

## 5. Жёсткие правила и триггеры reject

**Не обходится (см. §0):** фича реально в сборке и достижима · нет скрытой функциональности · review-notes не вводят в заблуждение · неиспользуемые entitlement’ы убраны (пример: `webcredentials` без логина) · ATT только после экрана-объяснения, не на старте · `UIBackgroundModes: audio` только с реальным playback и Now Playing · каждый высокорисковый доступ — на самой сильной фиче.

**Гайдлайны, под которые нельзя попасть:**

| Guideline | За что | Чем закрывается в концепте |
|---|---|---|
| 4.2 Minimum Functionality | Тонкая обёртка без самостоятельной ценности | Узкое УТП + фичи-якори, проходящие тест на подмену (фаза 2) |
| 4.3 Spam | Похожие клоны пачкой | Разные ниши и ядровые инсайты у каждого варианта; ниша далека от целевого приложения |
| 2.3.1 Hidden features | Скрытая/недостижимая функциональность | Каждая фича достижима за 2–3 тапа (фаза 3) |
| 5.1.1 Data & privacy | Доступ есть, фичи нет; пустой/невнятный usage-string | Карта «доступ → фича» без пустых строк; внятные privacy-strings |
| 2.5.4 Background modes | Неоправданный фоновый режим | Реальный обработчик/playback + Now Playing; лишние режимы не заявляем |
| 5.1.2 ATT / tracking | Трекинг без промпта или с мутным текстом | ATT-промпт после объяснения; IDFA реально в SDK |
| 3.1.1 IAP | Цифровой контент мимо IAP | Не продаём цифровое внутри, если не через StoreKit |

**Правило важнее всех таблиц:** до каждой фичи ревьюер должен дойти сам за 2–3 тапа без инструкции. Фича, которая в сборке есть, но спрятана, по последствиям равна её отсутствию.

## 6. Соглашения движка прототипа

Структура файлов платформы:

```
platform/
  kernel/                  ← общее для всех концептов, править только здесь
    page.html                оболочка итогового файла: шапка + 4 раздела
    base.css                 системный хром iOS + страница документа
    engine.js                фабрика прототипов: N устройств, у каждого свой журнал
    deliverable.md           СПЕКА ИТОГОВОГО ФАЙЛА — читать перед вёрсткой оболочки
    ios-chrome.md            канон системных компонентов
    chrome-gallery.html      живой стенд хрома
  concepts/<slug>/
    concept.json             единственный источник правды: доступы, экраны, прототипы
    screens/<id>.html        разметка экранов
    styles.css               только своё; имена не должны совпадать с ядром
    sections.html            блоки @overview:vision / @overview:arch + разделы «Документы»
    media.mjs                только данные, нарисованные кодом (схема, этикетка, карта)
    docs/01–06.md            вижен · архитектура · дизайн-система · референсы · аудит · App Store
  scripts/
    build.mjs                спека + экраны + ядро → dist/<slug>/index.html
    capture.mjs              playwright: PNG каждого экрана
    test-flows.mjs           playwright: флоу-проверки, выведенные из спеки
    lint-concept.mjs         сверка слоёв + мёртвый код + коллизии имён
    gen-docs.mjs             таблицы в docs/*.md из concept.json
```

Деплой — один сайт на все концепты: `npm run build:all` собирает галерею в корень `platform/dist/` и каждый концепт по своему подпути (`/petlya/`, `/<slug>/`). Конфиг — `netlify.toml` в корне репозитория, он единственный.

**Карточка App Store обязательна.** `docs/06-app-store.md` + блок `appStore` в `concept.json`: Name / Subtitle / Promotional Text / Keywords с лимитами 30 / 30 / 170 / 100, категории, App Privacy, демо-доступ для ревьюера, Review Notes. Это третья сверка концепта: стор, Info.plist и privacy-лейблы обязаны говорить одно и то же. Лимиты и совпадение «ATT ↔ трекинг в лейблах» проверяет `lint-concept.mjs`.

**Вход по номеру — всегда первые экраны.** Стартовый экран концепта — `phone` (номер) → `code` (SMS-код) → приложение. Компоненты в ядре, `start` в `concept.json` = `phone`. Без сервера — на SDK провайдера (VK ID / Firebase); в Review notes обязателен тестовый номер и код.

**Диплинков не делаем.** Universal Links, `associated-domains`, приём чужих ссылок, «отложенное» — вне области концептов. Если ключ есть в целевом наборе, он остаётся неотработанным: скажи об этом явно, решение за человеком. Заявить ключ без видимой фичи нельзя.

**Картинок не делаем.** Везде, где нужна фотография или иллюстрация, стоит плейсхолдер `.ph` — серое поле с иконкой камеры. Не генерируем визуал кодом, не ищем по стокам, не пишем генераторов. Исключение — данные, нарисованные кодом (схема, этикетка, карта): это содержимое экрана, а не визуал. Подробнее — `kernel/deliverable.md`.

**Интерфейс не выдумывается.** Системные компоненты берутся из `components.html` (сторибук iOS-хрома в корне репозитория), иконки — из спрайта Lucide (`kernel/icons.svg`). Своих SVG-путей и самодельных аналогов системных контролов в экранах быть не должно: нет компонента — заведи в сторибуке и ядре.

**Движок навигации (переиспользуй как есть):**
- Экраны — `<div class="screen" id="scr-<id>">`, активный `.is-on`, переключение классом.
- `data-go="<id>"` — переход; `data-back` — назад по стеку.
- `data-ask="<keys>|<then>|<else>"` — запрос доступа. `<keys>` — цепочка через `+` (напр. `speech+mic`): iOS показывает алерты подряд, отказ на любом шаге уводит на `<else>`. Отвеченный ключ второй раз системный alert не вызывает.
- `data-activate="<key>|<then>"` — entitlement (`audio`, `domains`): помечается granted без alert, сразу `<then>`.
- `data-jump="<id>"` — уйти с оверлея, не складывая его в историю.
- `data-toast="<текст>|<id>"` — подтверждение: та же полоска, что и отказ, но с галочкой и без ссылки в Настройки; 2,6 с против 4 с.
- Всё, что движок знает о концепте, приходит из `concept.json` через `window.__CONCEPT__`: `perms`, `titles`, `light`, `snack` / `snackOnce`, `tabs`, `parent` (родитель по IA — по нему считается возврат), `map`, `hero`. Руками в движке ничего про концепт не хардкодится.
- Прототипов на странице несколько, поэтому движок — **фабрика**: `[data-proto]` монтируется отдельно, со своим состоянием, своим алертом и своим журналом. Стартовое состояние задаёт движок, а не класс `is-on` в разметке.
- Fallback-атрибуты: `data-show-denied="<key>"` (показать при отказе), `data-hide-denied` (скрыть при отказе), `data-show-granted`, `data-switch="<key>"` (свитч отражает granted).
- Журнал доступов справа: считает уникальные запрошенные, порядок = порядок запроса, статусы granted/denied/idle.
- Контролы под устройством: «Показать, что нажимается» (`hints`), «Сменить тему» (`data-theme`), «Начать заново» (`reset`).
- HIG в разметке: хит-таргеты ≥44pt (утилита `.tap` кладёт псевдоэлемент `max(100%,44px)`); safe areas 54pt сверху / 34pt снизу; `prefers-reduced-motion` гасит анимации.

**Медиа.** Генератор в концепте (`media.mjs`) рисует **только данные**: схему, этикетку, карту. Чистые функции, детерминированный псевдослучай с seed (без `Math.random`, чтобы сборка была воспроизводима). Фотографий он не делает — вместо них плейсхолдер `.ph`.

**Тест (`test-flows.mjs`):** headless playwright, проверки выведены из спеки, а не перечислены руками. Обязательные — старт-экран, цепочки алертов, отказ → **видимый** fallback на том экране, куда привёл отказ, и для **каждого** триггера доступа, возврат по IA к объявленному `parent`, повторный вход без alert, `jump`/`back`, отсутствие битых переходов, достижимость всех ключей набора из UI, отсутствие в разметке доступов вне спеки, хит-таргеты ≥44pt, чистая консоль.

**Правило про fallback.** Отказ не только показывает подпись — он **убирает то, чего без доступа быть не может**: расстояния и точку «я» на карте без геопозиции, список найденных устройств без локальной сети, индикатор «Слушаю» без распознавания речи. Экран, который при отказе показывает прежние данные и рядом пишет «доступа нет», противоречит сам себе.

**Правило про ошибки.** Сбой фичи ≠ отказ доступа. Скан не распознал, страница не отдала разметку, источник удалён — это отдельные состояния с причиной человеческим языком, одним основным путём и одним запасным. Внешний вход (universal link, share sheet) рисуется целиком: экран-источник, состояние загрузки, результат — иначе фича выглядит кнопкой в настройках.

## 8. Разобранный пример — «Петля» (несёт набор ВК Видео)

- **Фаза 0.** Якорные: `UIBackgroundModes:audio` (высокий), `NSLocalNetwork` (Cast), `NSUserTracking` (ATT).
- **Фаза 1.** Ниша — школа вязания. Ядровый инсайт: **во время вязания руки заняты, телефон в них не держат.** Все якорные — «сильно»: фон (голос при погасшем экране), ТВ (телефон некуда класть, ТВ рядом), + добавлен `NSSpeechRecognition` под голосовой счётчик рядов как ядро.
- **Фаза 2.** УТП: «уроки вязания, которые можно смотреть, когда руки заняты спицами». Тест на подмену: убрать ТВ + фон + голосовой счётчик → остаётся обычный видеоплеер. Значит они и есть продукт.
- **Фаза 3.** camera → свой ракурс + скан этикетки; photo → фото прогресса в заметку; localnet → урок на ТВ; audio → голос в фоне/PiP; location → «пряжа рядом»; push → новый урок в курсе; domains → ссылка на урок; tracking → бесплатно с рекламой.
- **Фаза 4.** Каталог → статический `lessons.json`+mp4; комментарии → заметки к таймкоду (CoreData); эфиры → локальная запись; пуши → SDK; магазины → `MKLocalSearch`. Бэкенда — ноль.
- **Фазы 5–10.** 15 экранов, старт без промптов, у каждого отказа fallback, `webcredentials` убран (логина нет). Всё медиа — код (полотно, спицы, схема, этикетка, карта). Тест зелёный. ATT/push/location помечены «условными».

## 9. Финальный self-check (перед выдачей)

Смени роль на критика. Невыполненный пункт — это **возврат на указанную фазу**, а не примечание в отчёте.

**Продуктовая логика** → провал возвращает на фазу 1–2
- [ ] Пройден тест на подмену: без фич-якорей продукт разваливается в commodity.
- [ ] Пережиты все девять атак фазы 2, с конкретными ответами.
- [ ] Есть ответ, зачем открыть приложение на третий день.
- [ ] Ниша далека от целевого приложения и от соседних вариантов (4.3).
- [ ] УТП — одна фраза, и она читается с первого экрана за 5 секунд.

**Доступы** → провал возвращает на фазу 3
- [ ] Концепт несёт **весь** целевой набор — ни одного лишнего, ни одного недостающего.
- [ ] Каждый доступ = конкретная достижимая фича (2–3 тапа), не «причина».
- [ ] Все якорные (высокий/средний риск) доступы сидят на «сильных» фичах.
- [ ] По каждому «условному» доступу (ATT/push/гео/фон) назван минимум реализации, без которого он пустой.
- [ ] Неиспользуемые entitlement’ы убраны (`webcredentials` без логина и т.п.).
- [ ] На первом запуске нет ни одного permission-промпта.
- [ ] У каждого отказа — рабочий fallback, а не заглушка; повторно не переспрашиваем.

**Архитектура** → провал возвращает на фазу 4
- [ ] Ноль серверного кода: каждая серверная строка заменена клиентом или статикой.
- [ ] Нет логина и UGC — значит нет модерации и чужих данных.

**Дизайн** → провал возвращает на фазу 6 или 8
- [ ] Каждый экран просмотрен **по отдельности в полный размер**, не только в контактном листе.
- [ ] Два прохода вычитки подряд без новых дефектов серьёзнее придирки.
- [ ] Ни одного класса из таксономии фазы 8 не осталось в статусе «заметно».
- [ ] Один акцентный цвет; всё медиа сгенерировано кодом; хром — системный iOS.
- [ ] Хит-таргеты ≥44pt; safe areas соблюдены; статус-бар читается на всех экранах.

**Проверки** → провал возвращает на фазу 9–10
- [ ] Тест зелёный целиком и содержит проверки, специфичные для этого концепта.
- [ ] Скриптовая сверка доков с прототипом — без расхождений; ссылки и числа сходятся.
- [ ] Ни одного следа прошлой темы; мёртвые токены, классы и ассеты удалены.
- [ ] Консоль чистая.

**Честность отчёта**
- [ ] Таблица рисков без вранья; ни одной фичи «на бумаге, но не в сборке».
- [ ] Показаны отчёты по циклам (§7); что не проверено — названо непроверенным.

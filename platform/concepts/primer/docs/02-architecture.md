# Праймер — карта экранов и архитектура

Блоки `@generated:*` пересобираются командой `npm run docs -- primer` — внутрь них руками не пишем. Источник всех таблиц ниже — `concept.json` и разметка экранов.

## Слои

| Слой | Что внутри |
|---|---|
| UI | Экраны, tab bar, nav stack, system ask, snackbar. Только отображение — статусы доступов не хранит |
| Domain | Course · Step · PlaybackSession · Project · Palette · Swatch · Paint · PaintPack · MixRecipe · Note |
| Services | Permissions · Playback (`AVAudioSession`, `MPNowPlayingInfoCenter`, `MPRemoteCommandCenter`) · BarcodeScanner (`DataScannerViewController`) · MediaPicker (`PHPicker`) · PixelSampler (`CGImage`) · PaintMatcher (ΔE по Lab + линейное смешивание) · Push (SDK провайдера) · PhoneAuth (SDK провайдера) |
| Data | CoreData — проекты, палитры, свотчи, заметки к шагам, прогресс курса. Keychain — токен входа. FileManager — скачанные дорожки. `lessons.json` и `paints.json` — статические паки, только чтение |
| External | CDN контент-пака · APNs через SDK провайдера · SDK входа по номеру. Больше ничего: подбор аналога, ΔE и пропорции замеса считаются на устройстве |

`PermissionsService` — единственная точка запроса доступов. Экран не спрашивает систему сам: он вызывает сервис и получает результат, поэтому «спросили дважды» и «спросили не в момент действия» невозможны структурно.

## Информационная архитектура

Дерево выведено из разметки экранов и `concept.json`: вложенность — по `parent`, подпись «открывается» — реальный элемент прототипа. Первые два узла всегда одни и те же: вход по номеру (`phone` → `code`).

## Правила IA

**На первом запуске нет ни одного промпта.** Старт — `phone` → `code` → `lessons`. Доступы начинаются только после входа и только по явному жесту.

**Три вкладки, три роли.** `lessons` — что слушать. `projects` — чем красили. `settings` — что приложение делает без спроса (пуш, фоновое аудио). Доступы разложены по вкладкам так, что на одном экране не бывает больше двух разных ключей.

**Палитра — не общий блокнот, а часть проекта.** Поэтому оба «цветных» доступа (`camera`, `photo`) живут на `project`: это единственный экран, где у оттенка есть куда лечь. Карточка краски (`paint`) — тоже ребёнок `project`, а не `scan`: она открывается и сканом, и тапом по свотчу палитры, и ручным вводом кода, и во всех трёх случаях возврат должен вести в проект.

**Отказ убирает то, чего без доступа быть не может.**

| Отказ | Что исчезает | Что остаётся |
|---|---|---|
| `camera` | Строка «Сканировать баночку» на `project` и «Сканировать ещё баночку» на `paint`; кнопка «Сканировать ещё раз» на `scanfail` | Строка «Ввести код краски» → та же карточка. Аналоги и рецепт считаются по паку красок и от камеры не зависят |
| `photo` | Строка «Снять цвет с фото» на `project`; чип «Выбрать другое фото» на `dropper` | Уже снятые свотчи в палитре; добор оттенков сканом баночки или кодом вручную |
| `push` | Свитч остаётся выключенным | Новинки видно в списке курсов |
| `audio` | — | Entitlement: системного алерта нет. Без него звук обрывается на блокировке, и такую сборку не выпускают |

**Сбой фичи ≠ отказ доступа.** Два экрана ошибок отделены от отказов и выглядят по-разному, потому что и ситуации разные:

- `scanfail` — штрихкод не прочитался (наклейка залита краской). Баннер `.errbox` + один повтор + одна форма ручного ввода с теми же полями, что даёт автоматика. Тот же экран обслуживает и отказ камеры, но с другой причиной в баннере и без кнопки повтора.
- `dropfail` — оттенок снят, но ближайшая краска дальше ΔE 6,4. Это не ошибка чтения, а исход операции, поэтому полноэкранное состояние `.state`: причина, поле HEX и сохранение оттенка как своего.

**Возврат совпадает с объявленным `parent`.** `paint` и `dropper` открываются с нескольких сторон, поэтому уходят на цель через `data-jump`: оверлей (скан, галерея, ручной ввод) не остаётся в стеке, и «назад» из карточки краски ведёт в проект, а не в камеру.

**Повторно системный alert не показываем.** Отвеченный ключ второй раз не спрашивается — в fallback есть только ссылка «Открыть Настройки».

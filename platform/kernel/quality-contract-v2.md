# Quality contract v2

Версия 2 закрывает главный провал первого пайплайна: наличие полей больше не считается качеством. Концепт становится готовым только тогда, когда заявленная продуктовая модель доказана экранами, а интерфейс прошёл независимую приёмку.

## Глубокий модуль readiness

У модуля одна внешняя interface: `assessConceptReadiness(spec) → { issues, summary }`. За ней скрыты четыре группы проверок:

1. **Product truth** — конкретная ситуация, наблюдаемый результат, ядровой цикл и причины возврата без шаблонных формулировок.
2. **Reference fit** — для мимикрии каждый обязательный паттерн референса связан с экраном и поведением; корневая навигация покрывает роли архетипа.
3. **Screen truth** — у каждого экрана есть роль в навигации, иерархия, типичный, плотный/длинный и failure-case.
4. **Review evidence** — минимум две полные визуальные итерации; первая содержит найденные и исправленные дефекты, последняя закрыта без блокеров и заметных дефектов.

Структурная валидность остаётся в `validate()`. Readiness — отдельные ворота `npm run proof`: черновик можно собирать и смотреть, но `npm run check` и публикация его не пропустят.

## UI contract v3

Новые концепты используют `uiContractVersion: 3`.

- `navigation`: `root`, `push`, `modal`, `fullscreen` или `system`;
- `hierarchy`: видимые primary/secondary regions;
- `contentCases`: объекты трёх типов — `typical`, `stress`, `failure`;
- главное действие размечено `data-primary` и встречается ровно один раз;
- root-экраны имеют одинаковый tab bar; push/fullscreen не дублируют его;
- inline-style, emoji-заглушки, `.ph` и icon-only controls без `aria-label` запрещены.

Это не гарантирует вкус автоматически. Контракт убирает повторявшиеся механические причины нейрослопа и заставляет визуальную критику быть артефактом pipeline, а не обещанием в отчёте.

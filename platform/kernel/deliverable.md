# Формат итогового файла

Единственный артефакт, который отдаётся наружу, — **один самодостаточный `index.html`** плюс `assets/` и `docs/` рядом. Открывается по `file://`, деплоится копированием, не требует сборки на стороне получателя.

Формат общий для всех концептов: он живёт в `kernel/page.html` + `kernel/base.css`, а не в концепте. Концепт поставляет содержимое — экраны, спеку, документы, — но не структуру страницы.

---

## Шапка

Липкая, три зоны:

| Зона | Содержимое |
|---|---|
| Слева | Имя приложения |
| По центру | `Overview · Прототипы · Экраны · Документы` |
| Справа | «Скачать файлы» → `docs/<slug>-docs.zip` |

Разделы — **вкладки**, а не якоря: одновременно виден ровно один. Текущий раздел записывается в hash, поэтому ссылкой можно прислать конкретную вкладку.

## 1. Overview

Сразу под героем выводится **продуктовый контракт** из `concept.json`: аудитория, ситуация, проблема, обещание, отличие, ядровой цикл и non-goals. Сборка падает, если контракт неполон: технически корректный, но размытый концепт не считается готовым.

Первый экран отвечает на три вопроса сразу, без прокрутки.

```
┌─────────────────┬──────────────┬────────────────────┐
│  Заголовок      │              │  Список доступов   │
│  Дек            │  Устройство  │  (журнал запросов) │
│  Счётчик        │              │  Пояснение         │
└─────────────────┴──────────────┴────────────────────┘
```

- **Слева** — `heroTitle` и `heroDeck` из `concept.json`. Одно предложение о продукте, не абзац.
- **По центру** — геройский прототип: все экраны концепта, старт с первого экрана приложения.
- **Справа** — живой журнал: ключ, статус, номер и экран запроса. Он и есть главный артефакт — по нему видно, что каждый доступ спрошен в момент действия.

Ниже — три панели:

| Панель | Откуда |
|---|---|
| «Продуктовый вижен» | `sections.html`, блок `<!-- @overview:vision -->` |
| **«Информационная архитектура»** | генерируется — дерево экранов, см. ниже |
| «Архитектура и ключевые сценарии» | `sections.html`, блок `<!-- @overview:arch -->` |

## 2. Прототипы

Сетка карточек: **один сценарий — один кликабельный прототип со своим журналом**. Название, подзаголовок в одну строку, устройство, счётчик запрошенных доступов, контролы.

Сценарий — это срез: свой стартовый экран и свой набор экранов. Ревьюер проходит путь целиком и видит ровно те доступы, которые этот путь запрашивает, — а не суммарный журнал по всему приложению.

## 3. Экраны

Плотная сетка всех экранов концепта, включая состояния отказа и ошибок. Клик открывает экран в геройском прототипе на Overview — журнал при этом **не** сбрасывается.

## 4. Документы

Ссылки на `docs/01–06` + ZIP, затем **«Карта экранов и переходов»** (см. ниже) и таблицы концепта: матрица доступов, «почему нет бэкенда», экраны и доступы, дизайн-токены. Всё генерируется из `concept.json`, руками не пишется.

## Карта экранов: откуда куда попадаем и что можно сделать

Два представления, оба **выводятся из разметки экранов и спеки** (`scripts/screen-map.mjs`), руками не рисуются:

| Где | Что | Отвечает на вопрос |
|---|---|---|
| Overview, панель «Информационная архитектура» | дерево экранов по `parent`: тип, доступы, чем экран открывается, куда ведёт вбок | где экран лежит и как до него дойти |
| Документы, «Карта экранов и переходов» | таблица: экран → действие → цель → доступ → тип перехода | что можно сделать и куда это приводит |

Источник — те же байты, из которых собран прототип: `data-go` / `data-jump` / `data-ask="ключи|цель|отказ"` / `data-activate` / `data-toast` / `data-back` в разметке плюс `parent`, `tabs`, `start` и `permissions` в спеке. Подпись действия — `aria-label` элемента или его первая текстовая строка. Вкладки таб-бара в таблицу не идут: они одинаковы на всех экранах и ведут в корни разделов.

Рукописную схему навигации в доках держать не нужно — в `docs/02-architecture.md` для этого два блока: `<!-- @generated:ia-tree -->` и `<!-- @generated:transitions -->`, они пересобираются `npm run docs -- <slug>`.

**Сборка падает**, если карта не сходится: переход в экран, которого нет в спеке; экран, недостижимый из `start` (в него не ведёт ни один переход); отказ в доступе, ведущий на экран, где `data-show-denied` для этого ключа не объявлен. Первое и третье ловил тест, второе — не ловил никто: непройденный экран в собранном файле выглядит как полноценный.

## Прототипы в `concept.json`

```json
"prototypes": [
  { "id": "all", "hero": true, "label": "Весь продукт",
    "note": "Все экраны и все десять доступов",
    "start": "lessons", "screens": ["lessons", "lesson", "…"] },

  { "id": "evening", "label": "Вечер с вязанием",
    "note": "Урок на ТВ, голос в фоне, счёт рядов без рук",
    "start": "lessons", "screens": ["lessons", "lesson", "cast", "counter", "pip", "background"] },

  { "id": "profile", "label": "Профиль: пуш, ATT, ссылки",
    "start": "settings",
    "screens": ["settings", "ads", "lessons", "cast", "background", "deeplink", "saved"],
    "stops":   ["lessons", "cast", "background", "deeplink", "saved"] }
]
```

- `hero: true` — прототип на Overview. Ровно один; он обязан содержать **все** экраны спеки.
- `screens` — срез сценария. Экран рендерится в каждый прототип, где он есть; id на странице уникальны (`pr-<proto>-<screen>`).
- `stops` — экраны-тупики: показываем, куда ведёт строка, но дальше не пускаем. Так срез остаётся замкнутым, не втягивая всё приложение.

**Сборка падает**, если сценарий не замкнут: переход в экран, которого в срезе нет, — это тупик, невидимый в собранном файле. Исключение одно — вкладки таб-бара чужих разделов: они гасятся (`.is-off`), показывая, где мы, но никуда не ведут.

## Откуда берётся интерфейс

Системные компоненты — из [`components.html`](../../components.html): сторибук iOS-хрома, перенесённый в `kernel/base.css`. Иконки — спрайт Lucide (`kernel/icons.svg`, `node scripts/gen-icons.mjs`), подключается инлайном при сборке; в разметке `<svg class="ico-svg"><use href="#i-camera"/></svg>`.

Смысл и состояние каждого нового экрана фиксируются в [`ui-contract.md`](ui-contract.md). Версия `uiContractVersion: 1` требует для экрана паттерн, продуктовую цель, основное действие и предусмотренные состояния; сборка дополнительно проверяет, что заявленное основное действие действительно видно в разметке.

Рисовать SVG-пути руками и изобретать компоненты в экране концепта — нельзя. Нет нужного — заводится в сторибуке и ядре, потом используется.

## Карточка App Store — обязательная часть концепта

Концепт не закончен, пока не заполнена карточка стора: `docs/06-app-store.md` + блок `appStore` в `concept.json`.

Смысл не в маркетинге. Карточка — это **третья сверка**: строки в сторе, ключи в Info.plist и privacy-лейблы обязаны говорить одно и то же. Расхождение между ними возвращает сборку чаще, чем сами доступы.

Что входит:

| Блок | Откуда | Проверка |
|---|---|---|
| Name, Subtitle, Promotional Text, Keywords | `appStore` в спеке | лимиты 30 / 30 / 170 / 100 — считает линтер |
| Категории, возрастной рейтинг, цена, URL, шифрование | `appStore` | — |
| Описание | текст дока | структура «фича — что она даёт», не перечень |
| **App Privacy** | `appStore.privacy` | трекинг в лейблах обязан совпадать с наличием ATT в наборе — линтер |
| **Демо-доступ** | `appStore.reviewAccount` | первый экран — вход по номеру, без тестового номера ревьюер не пройдёт |
| Review Notes | `reviewNote` у доступов | генерируется из спеки, руками не дублируется |
| Скриншоты и превью | текст дока | порядок кадров = порядок ценности |

Линтер также ловит пробел после запятой в keywords (съедает символ лимита) и слова, дублирующие Name/Subtitle — Apple индексирует их и так.

## Первые экраны — вход по номеру телефона

Любой концепт начинается со **входа по номеру**: `phone` (номер + код страны) → `code` (четыре ячейки SMS-кода) → первый экран приложения. Стартовый экран в `concept.json` — всегда `phone`. Таб-бара на этих двух экранах нет, permission-алертов тоже: доступы начинаются после входа.

Компоненты — в ядре: `.auth-mark`, `.auth-cc`, `.field-input.auth-num`, `.otp` / `.otp-cell` (`.is-filled`, `.is-active`).

Без сервера это живёт на SDK провайдера аутентификации (VK ID / Firebase Phone Auth): токен в Keychain, своего бэкенда по-прежнему нет. В Review notes обязателен тестовый номер и код — иначе ревьюер упрётся в первый экран.

## Диплинков не делаем

Universal Links, `associated-domains`, приём чужих ссылок, экраны-превью и «отложенное» — **вне области концептов**. Не проектируем, не рисуем, не заявляем ключ.

Если ключ `com.apple.developer.associated-domains` есть в целевом наборе — он остаётся **неотработанным**: сообщи об этом вместе с результатом, чтобы решение принял человек. Заявлять ключ без видимой фичи нельзя, это прямое нарушение правила «фича, а не причина».

## Визуал — только плейсхолдер

**Фотографии и иллюстрации в концептах не делаются.** Ни генерации кодом, ни поиска по стокам,
ни скриптов, которые их рисуют. Везде, где по макету должна быть картинка, стоит плейсхолдер:
**серое поле с иконкой камеры** — класс `.ph` (`.ph.on-dark` на тёмной подложке).

```html
<div class="ph" style="height:172px;border-radius:12px"></div>
<div class="lrow-thumb ph"></div>
```

Почему так: картинка — это контент, а не работа платформы. Концепт показывает структуру,
доступы и поведение; подбор визуала — отдельная задача и отдельные права. Плейсхолдер
честнее любой заглушки из интернета и не создаёт вопросов по лицензиям.

Исключение — **данные, нарисованные кодом**: схема вязания, этикетка мотка, карта кварталов.
Это не «визуал», а содержимое экрана, без которого фича непонятна.

## Что проверяется механически

`node scripts/lint-concept.mjs <slug> --kernel` — расхождения спеки, разметки и стилей; мёртвый код; **коллизии имён классов** между ядром и концептом (класс, объявленный с нуля в обоих местах, молча ломает страницу).

`node scripts/test-flows.mjs <slug>` — флоу по геройскому прототипу: старт, цепочки алертов, отказ → видимый fallback на каждом триггере, возврат по IA к объявленному родителю, отсутствие битых переходов, достижимость всех ключей, хит-таргеты ≥ 44pt, чистая консоль.

## Чего в этом файле не бывает

- Двух конкурирующих артефактов: лендинга и доски. Файл один.
- Прототипа, до которого надо докручивать страницу: устройство — на первом экране.
- Сценария без журнала: каждый прототип показывает, что он запросил.
- Экрана, который есть в спеке, но не собран, — и наоборот. Линтер ловит оба направления.

# Как изменился нативный пайплайн: от «Эстафеты» к «Полке»

Документ сравнивает две **нативные** реализации в ветке `codex/native-concept-pipeline-v2`:

- предыдущий pipeline v2 в `ios-concepts/native/`, на котором была собрана «Эстафета»;
- текущий authored-SwiftUI pipeline в `platform/`, на котором собрана «Полка».

HTML-пайплайн в этом сравнении не участвует.

## Коротко

Предыдущая версия пыталась генерировать почти всё приложение из структурированных контрактов. Она хорошо проверяла полноту спецификации, но одновременно принимала слишком много продуктовых и интерфейсных решений. В результате UI «Эстафеты» был технически полный, но тяжёлый, однообразный и плохо поддавался ручной доводке.

Новая версия меняет seam:

> генератор владеет только тем, что можно однозначно вывести из фактов; продуктовый UI полностью принадлежит авторскому SwiftUI.

Пайплайн больше не генерирует экраны, навигацию, reducers и визуальную композицию. Он собирает Xcode-проект, платформенную конфигурацию и fixtures, а также проверяет, что каждый capability действительно связан с продуктовой фичей и runtime adapter.

## Было: pipeline «Эстафеты»

Основной поток выглядел так:

```text
spec
  → Product Core
  → Capability Plan
  → Full Contract
  → Product Blueprint
  → Product UI Contract
  → Native Kernel compiler
  → сгенерированные SwiftUI + Store + Shell + XCUI
  → Xcode build
  → screenshots и visual review packet
```

### Чем владел компилятор

`native-kernel-v2` объявлял compiler-owned сразу несколько крупных частей приложения:

- app shell и авторизация;
- маршруты;
- reducers и product state;
- permission wiring;
- capture-инструментарий;
- XCUI skeleton;
- тела продуктовых экранов.

Сгенерированное приложение сохранялось в `ios-concepts/native/apps/estafeta/`. При следующей materialization каталог удалялся и создавался заново, поэтому ручная переработка экранов конфликтовала с моделью владения пайплайна.

### Почему результат не устроил

Проблема была не в отсутствии проверок. Наоборот, проверок и промежуточных моделей стало слишком много.

1. **Один продукт описывался несколько раз.** Product Core, Blueprint, Full Contract и UI Contract повторяли сущности, действия, поверхности и состояния в разных формах.
2. **Изменение UI проходило через слишком длинный путь.** Чтобы поправить композицию экрана, приходилось менять контракт или генератор, пересобирать все производные артефакты и только затем смотреть SwiftUI.
3. **Screen recipe стал скрытым шаблоном.** Формально приложение генерировалось из продукта, но на практике экран сводился к ограниченному набору секций, карточек и стандартных состояний.
4. **Генератор якорил плохие решения.** После генерации было проще полировать существующую раскладку, чем пересобрать экран вокруг пользовательской задачи.
5. **Capability coverage влияло на структуру UI.** Большое число доступов часто превращалось в большое число однотипных действий и технических поверхностей.
6. **Visual review работал слишком поздно.** Он мог обнаружить слабую иерархию на готовых PNG, но не исправлял саму причину — генератор уже выбрал композицию.

Итог: высокая формальная полнота, но неглубокий интерфейс самого pipeline-модуля. Чтобы получить новый визуальный результат, требовалось знать и менять значительную часть его реализации.

## Стало: authored-SwiftUI pipeline «Полки»

Новый поток короче:

```text
concept.json
  ├─→ ux-spec: модель мира, сценарии, навигация, capability coverage
  ├─→ platform facts: Info.plist, entitlements, background modes
  ├─→ Fixtures.swift
  └─→ authored SwiftUI sources
          + shared AccessRuntime
          → Xcode project
          → simulator build и visual review
```

### Новый seam

У пайплайна теперь три чётких модуля.

#### 1. Product facts

Интерфейс: `concepts/<slug>/concept.json`.

Содержит:

- модель мира и продуктовые действия;
- экраны и граф переходов;
- набор capability с объяснением, жестом и fallback;
- acceptance-сценарии;
- fixtures и пользовательские тексты.

Он отвечает на вопрос **что должно существовать в продукте**, но не задаёт SwiftUI-композицию.

#### 2. Authored product UI

Интерфейс: `native-apps/<slug>/Sources/*.swift`.

Здесь вручную принимаются все решения, которые нельзя корректно вывести из JSON:

- информационная и визуальная иерархия;
- TabView и NavigationStack;
- композиция каждого экрана;
- размеры, ритм, типографика и цвет;
- модальные сценарии и task flows;
- состояние продукта и наблюдаемый результат действий.

Пайплайн не знает про «правильное количество карточек», обязательный large title, recipe экрана или универсальный UI kit.

#### 3. Native platform

Интерфейс сборки:

```bash
npm run spec -- <slug>
npm run app -- <slug>
npm run app:run -- <slug>
```

Реализация скрывает:

- создание Xcode-проекта;
- генерацию Info.plist;
- генерацию entitlements;
- UIBackgroundModes и BGTask identifiers;
- перенос fixtures в Swift;
- реальные iOS capability adapters;
- установку и запуск приложения в симуляторе.

Это глубокий модуль: вызывающему коду не нужно знать устройство pbxproj, правила plist или конкретные системные framework.

## Что теперь генерируется, а что нет

| Область | «Эстафета» | «Полка» |
|---|---|---|
| Продуктовые экраны | Генерировались из контрактов и recipes | Полностью авторский SwiftUI |
| Навигация | Compiler-owned | Авторская |
| Product Store / reducers | Генерировались | Пишутся под доменную модель приложения |
| Shell | Общий сгенерированный | Минимальный authored app root |
| Визуальный язык | Shared DesignSystem + profile | Локальные токены и компоненты приложения |
| Системные доступы | Capability plan + generated wiring | Общий runtime, вызываемый из authored features |
| Info.plist | Генерировался | Генерируется |
| Entitlements | Генерировались | Генерируются |
| Fixtures | Производные контракты | Генерируются напрямую из `concept.json` |
| Xcode project | Генерировался | Генерируется |
| Capture | Каталог генерировался из surface/state matrix | Launch arguments определяет само приложение |
| UI-проверка | Контрактные audits + XCUI + screenshots | UX-spec + build guard + screenshots и ручная визуальная приемка |

## Что удалено из активного пути

Следующие слои больше не нужны для сборки нового приложения:

- `ProductBlueprints/<app>.json`;
- `ProductUIContracts/<app>.json`;
- Full Contract и Slice Contract;
- компиляция SwiftUI-экранов в `native-kernel-v2`;
- screen recipes как вход нативного renderer;
- compiler-owned routes и reducers;
- обязательная общая визуальная система для разных продуктов;
- генерируемый developer kit из большого числа производных документов.

Старый `ios-concepts/native/` удалён из ветки: он больше не участвует в сборке и не может случайно стать вторым публичным интерфейсом. Новые приложения собираются только через `platform/scripts/build-app.mjs`.

## Что сохранилось

Упрощение не означает отказ от проверяемости.

- `concept.json` остаётся источником продуктовых фактов.
- Capability нельзя заявить без фичи, fallback и действия модели мира.
- Usage descriptions не пишутся отдельно в Xcode и не расходятся со спецификацией.
- Entitlements и background modes выводятся из единого `capability-map.json`.
- Fixture-контент не копируется вручную в Swift.
- Есть детерминированные launch arguments для granted/denied и capture-состояний.
- Результат обязательно собирается и проверяется глазами в симуляторе.

## Что стало строже на примере 22 capability

В версии «Эстафеты» наличие capability plan ещё не гарантировало качественную продуктовую интеграцию: технически ключ мог присутствовать в плане и проявляться отдельной однотипной кнопкой.

В новой версии сборка проверяет четыре независимых условия для каждого ключа:

1. ключ объявлен в `concept.json` и связан с действием модели мира;
2. ключ существует в authored `Access`;
3. authored SwiftUI действительно вызывает его из достижимой фичи;
4. shared runtime содержит явный adapter, а platform map знает его plist/entitlement.

Фиктивный `default: true` для entitlement и background capability удалён. Если реальной операции нет, runtime возвращает отказ, а сборщик не принимает отсутствующий adapter.

Для «Полки» проверка сейчас выдаёт:

```text
permissions: 22
coveredCapabilities: 22
usageKeys: 9
entitlements: 8
backgroundModes: remote-notification, fetch, audio, voip
UX gaps: 0
```

При этом capability распределены по продукту, а не собраны в технической витрине:

- камера, фото, App Groups и Keychain — добавление вещи;
- микрофон, speech, audio и VoIP — договорённость с владельцем;
- push, communication и remote notifications — ответы и статусы;
- location, calendar, Wi‑Fi Info, Hotspot, Face ID и Autofill — передача;
- tracking — объяснённая персонализация поиска;
- fetch и BGTask — актуальность полки и возвратов;
- Associated Domains — ссылка на конкретную вещь;
- Contacts — закрытый круг друзей.

## Что изменилось в цикле разработки

### Раньше

1. Изменить spec или один из контрактов.
2. Перекомпилировать Blueprint, UI Contract и Native Kernel.
3. Получить заново сгенерированные Swift-файлы.
4. Пройти audits и XCUI.
5. Увидеть визуальную проблему на screenshots.
6. Решать, в каком из генераторов её исправлять.

### Теперь

1. Описать модель мира, действия и capability в `concept.json`.
2. Запустить `npm run spec -- <slug>` и закрыть semantic gaps.
3. Спроектировать SwiftUI непосредственно в `native-apps/<slug>/Sources/`.
4. Запустить `npm run app:run -- <slug>`.
5. Снять root- и task-экраны, посмотреть их глазами и поправить SwiftUI на месте.

Путь от визуального дефекта до места исправления стал прямым: экран исправляется в файле экрана, системный доступ — в runtime adapter, plist-факт — в capability map.

## Ограничения текущей версии

- Pipeline проверяет наличие и связность 22 capability, но часть entitlements окончательно проверяется только на подписанном физическом устройстве.
- Push требует APNs-конфигурации, Universal Links — AASA, а Wi‑Fi/Hotspot не подтверждаются полноценно в симуляторе.
- XCUI-покрытие новой версии пока легче, чем у pipeline «Эстафеты»; это осознанная следующая зона усиления. Возвращать генерацию UI ради этого не нужно — тесты должны идти через тот же authored interface приложения.

## Критерий успеха новой архитектуры

Новый pipeline считается успешным не тогда, когда умеет сгенерировать больше Swift-кода, а когда новое приложение можно свободно спроектировать, собрать и визуально довести, не меняя генератор экранов.

Если для нового продукта требуется другой feed, профиль, навигация или task flow, меняется authored SwiftUI. Если появляется новый системный capability, один раз расширяются platform map и runtime adapter. Это и есть новый seam.
